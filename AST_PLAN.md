# Rust AST normalization plan

Make the Rust AST the primary card representation, with a much smaller vocabulary of generic operations. Preserve coverage of every card supported by the existing parser and use the existing grammar and Rust conversion pipeline to verify that coverage. Complete normalization first; implement the remaining Cantrip backend later. Work in batches of related source forms with focused checks during iteration and broader validation at meaningful integration points.

The priorities, in order, are:

1. A useful, typed Rust representation of the AST.
2. Preservation of all currently supported cards, verified through existing code and corpus data.
3. Generic operations that minimize distinct forms without losing rules semantics.
4. Fast implementation and enough validation to establish correctness, with expensive checks run only when their coverage is relevant.

### Two different finish lines

Reaching the unified AST quickly requires separating two things this plan has treated as one:

- **Unified**: the record is represented entirely in the new AST, in one schema, with typed operands and bound references where they can be bound. Some nodes may be generated named forms that have not been reduced to generic operations.
- **Reduced**: every node is a reviewed generic operation. This is what "complete" means today.

Unification can be automatic and total. Reduction is semantic work and can then proceed in priority order, on a stable format that consumers can already use. The existing rule stands: a legacy escape or opaque form never counts as normalized. A generated named form is reported as unified and unreduced, never as complete, and the two counts stay separate in every report. Mixing them would repeat the "complete means correct" mistake below.

### Automation tiers

Each form on no complete card falls into one class. The class is mechanical: it comes from the Rust field signature in `mtg_types.rs` and the variant name, which `ast pipeline-candidates` already parses with `syn`.

| Tier | Class | Forms | Complete if finished | How it is automated |
|---|---|---:|---:|---|
| 1 | Generated named form for everything | 6,429 | unified 33,529 (100%); reduced unchanged | Generate one lowering per variant from the enum definitions. Recursively lower operands; emit `Named { source_type, form, operands }`. |
| 2 | Fieldless leaves | 1,796 | 17,453 (52.1%) | Derive vocabularies from enums: subtypes, counter types and similar become one parameterized node, with no per-variant code. |
| 3 | Layout wrappers | 17 | enables the 1,343 records at 0% | One generic face wrapper, keeping layout as data. Do this early: these records expose forms no complete card shows. |
| 4 | Same signature as a proven form | 1,277 | 22,170 (66.1%) with tier 2 | `pipeline-candidates` drafts registry rows by copying the proven sibling's shape; generated fixtures and the literal audit check them; a reviewer accepts batches, not rows. |
| 5 | Reference forms (`Ref_`, `Trigger_`, `ThisWay`, `That…`) | 535 | 23,118 (68.9%) with tiers 2 and 4 | One resolver over the existing scopes, driven by a table from form to the result or binding it reads. |
| 6 | New signatures, including the 17 wrappers | 2,820 | 33,529 (100%) | The long tail. Stays as generated named forms and is reduced by consumer need, in greedy order. |

The record counts in tiers 2, 4 and 5 are cumulative upper bounds from full-tree forms: a form proven on one card may still fail in another context, and 65 incomplete records have no unproven form at all. A matching signature also proves nothing about meaning, which is why tier 4 needs review. Re-measure after each tier rather than trusting these projections.

### Order of work

1. **Generate tier 1. Done, schema 24.** All 33,529 records lower, validate, and round-trip through JSON, bincode and RON, and `ast check` and `pipeline-check` report `unified` separately and agree on every record. This did not use the generated per-variant code proposed earlier: `crate::unified` walks the serde inspection of the source, so it is total by construction, needs no `syn` build step, and adds no compile time. Strict lowering runs first and is unchanged, so no `Card` record changed state. Failed actions become `Operation::Named` inside otherwise reduced abilities, failed rules become `Ability::Named`, and anything the validator rejects falls back to a whole named rule. Named operands lower with no surrounding bindings, so a reference that needs them stays a visible `Form` and cannot attach to the wrong antecedent. `validate::card` rejects `Named`, so a named form can never pass as complete. Measured: 158,320 unreduced nodes across 7,195 distinct forms. Each record's `named` map is the true worklist and replaces the "unproven" estimate. The `cantrip` feature does not compile, and did not before this change, with the same errors at the previous commit; adapters stay out of scope until a backend needs them.
2. **Generate tier 2 and tier 3. Done.** Tier 3 landed with tier 1: `UnifiedCard` holds any layout as ordinary `Card` faces plus layout data, from one generic walk with no per-layout code, which raised `complete` from 15,273 to 15,505 with no losses. Tier 2's vocabularies are derived from `mtg_types.rs` at build time. They removed 613 distinct named forms and **changed no record**: the projection of 17,453 was wrong, because those leaves already lowered and only looked unproven beneath failed parents. No diagnostic has ever named `SubType`, `CreatureType`, `CardType` or `CounterType`.
3. **Registry drafter. Done, as reviewed primitives rather than copied siblings.** The largest blocker groups are atomic rules actions, keyword abilities and events, which have no proven sibling to copy. `ast primitive-draft` writes candidate rows from true blockers, with signatures and Oracle hit rates, and accepted rows go in `rewrites/primitives.json5`. One generic path lowers `Operation`, `Ability` and `EventSpec` primitives. Unlike `Named`, every operand must bind in the enclosing scope, so a primitive holds no unreduced form. `ast primitive-audit` checks every use against Oracle text. 373 rows raised `complete` to 18,728.
4. **Table-driven resolver. Done for the references that block the most records.** A trigger row's `binds` lists what the event supplies, so `Trigger_ThatPlayer` and similar resolve from data. Events with two candidate objects bind no object: "that creature" stays blocked rather than guessed. Schema 26 added `PlayerRef::DefendingPlayerOf` and `ObjectRef::EventDestination`, the new object a zone change produced. `Trigger_ThatGraveyardCard` is constrained to the graveyard, so a discard another effect sent elsewhere is not exiled from that other zone.
5. **Reduce tier 6 in greedy order, in progress.** Stop when consumers no longer need a given form reduced. Done so far: sagas as one chapter trigger per number; damage prevention as `ReplacementEvent::Damage` with `Operation::CreateReplacement`, which maps about 50 source variants onto the existing `DamageEvent`; spells with two resolutions as `Ability::CostBranch`, so a kicked target is announced only when kicked. `Primitive` now also covers `Cost`, `Condition`, `Permanents`, `Players`, `GameNumber`, `LayerEffect` and `DeckConstruction`, and a primitive may hold a nested `Program` or a bound `Operand::Term` from the registry's `terms` list. Unlike a `Form`, a term fails if anything inside it does not bind. This one change took `complete` from 19,299 to 20,792. Schema 29 adds reflexive triggers: a `Reflexive_<Base>_When<Event>` form is decoded from its variant name into its base action or cost, then `Operation::ReflexiveTrigger`, with no per-variant code. It also adds `Operation::ReturnAfter` for "exile until", state-based `Duration` forms, and a binding from "sacrificed this way" or "tapped this way" to the ordinary action that did it, which replaces the failure the shadowing rule used to give. Forms that test what happened, such as `WhenACardOfTypeIsDiscardedThisWay`, stay blocked. Schema 30 adds `EntryState` for how an object enters, `TokenRecipe::Copy` for token copies, and `Operation::BindValue` with `Expr::BoundValue` for a number fixed partway through a resolution. Schema 31 treats a revealed cohort as an inspected one, so reveal steps reuse inspection's scopes through a table of name aliases, and adds `Instruction::ChooseOne` for a choice of actions made on resolution. Schema 32 adds `Instruction::ForEachPlayer`, which binds each player in turn, so a per-player action now states its iteration instead of being refused for lacking a batch policy. Schema 33 adds `Instruction::Repeatable` for an action a player may repeat, `Ability::Class` with its levels, and the activation limits and keywords that exhaust and power-up abilities need. Schema 34 adds a total on `TargetSpec`, split when the targets are chosen (601.2d), with `Expr::DistributedShare` read per recipient, so one operation over the slot gives each target its part. `Count::Between` covers "one, two, or three". Rhino, Terrible Trampler stays blocked: its source does not say which of two target slots receives the split. Schema 35 lowers every `Replace...` form through one generic path in `lower_replace.rs`. A replacement body spells ordinary actions in about 50 enums of its own, so each step is retagged to `Action` and decoded, with no per-family code, and only forms that change the event are table-driven. Damage events reuse the prevention family the same way, zone changes reuse `EventSpec::ZoneChange`, and the other events are reviewed rows behind `ReplacementEvent::Primitive`. A body's meaning differs by family, which a test pins: damage and zone-change bodies are explicit, while elsewhere an action list happens instead of the event unless it names the event's fate, so "gain twice that much life instead" cancels the original gain. Rows that hide occurrence history, such as "the first card you draw each turn", were left out. Schema 36 adds `CostPart::Reveal` and `CostPart::Repeated`, `Operation::SetLifeTotal`, the extra zones of a search, `Expr::DieResult` for "the result", and a `once` flag on created triggers for "your next spell this turn". Schema 38 adds `Destination::OwnersLibraryShuffled`, since "shuffle it into its owner's library" is one action, a `ModeSelection.implied` flag for a target that decides its own mode, and primitives in `RuleChange`, `PlayerRule`, `ManaUse` and activation modifiers, which took one batch of reviewed rows to 25,753. Schema 39 adds a per-scope record of what each resolution did, so `Expr::Performed`, `ObjectFilter::DamagedBy` and `ObjectSet::Affected` read "life lost this way", "each creature dealt damage this way" and "those creatures" from the instruction that did it. `PlayerRef::FirstWilling` is the payer of "any player may". `ObjectRef::Primitive` and `PlayerRef::Primitive` hold rules-defined references such as the creature a soulbond card is paired with. `ReplacementActive::Everywhere` covers "from anywhere". **Mass rows, schema 53.** `propose.py`-style drafting keeps a row only when a word from the form's own name is in every card's Oracle text. 1,336 such rows took complete from 29,034 to 30,452 with no losses, and every use still passes `primitive-audit`. These rows name atoms; they do not reduce them, so "complete with no primitive" did not move. Treat them as staged: each row is a candidate for a table row or a generic op. Rows the audits and tests refused stay out: damage and first-time triggers, `ThisGame` and `ThisCombat` history, and single-use cast permissions, which need usage accounting.

**Choices, schema 55, checked against Forge.** Forge's scripts in `forge-gui/res/cardsfolder` are a working reference for a generic form, so read the same cards there before settling a shape. For choices they showed:

| Forge | This AST |
| --- | --- |
| `ChooseCard` with `Defined$ Player`, `ChosenCard` accumulating over choosers | `ForEachPlayer` around `ChooseObjects`; the choice reads after the loop as a set. It is never one object, which the validator enforces |

| `WithTotalPower$` | The existing `SelectionConstraint::TotalProperty` |

Forge folds "you may choose X, if you do return it" into one optional move. Here it stays a cost whose body holds the choice, so `CostWasPaid` still reads it. Table `Choose` rows and `note_choice` pick the slot from the zone chosen from. Choosing one of an earlier set narrows the singular reference only: Benthic Anomaly copies the one pick and totals the whole set.

**Modes and delayed events, schema 57.** Forge has one `Charm` with options (`CharmNum`, `Chooser$`, `Random$`, `CanRepeatModes$`, `Pawprint$`), so `ModeSelection` carries the same options as data: `chooser`, `random`, `budget` and `may_decline`, with a `weight` and a `requires` on each `Mode`. New forms are rows in `programs.json5`. `CreateDelayedTrigger` now takes any event; its body still reads only the creator's scope, so a body that names the future event stays blocked instead of binding wrongly. "Next ... this turn" is a one-shot `CreateTrigger`, and the extra turn a row creates is a `DelayedStart`.

### Damage as one query, schema 59

Damage now lowers through one table on source, amount and recipient, the way
Forge's `DealDamage` takes `DamageSource$`, `NumDmg$` and `Defined$`. Forms that
differ only in who deals the damage share `deal`. `DealDamageWith` carries the
three riders as data: `DividedEvenly` (`DivideEvenly$`), `ExcessTo`
(`ExcessDamage$`) and `Prevented`.

History is one `EventSpec::Damage` query. Forms pick a window (`ThisTurn`,
`LastTurn`, `ThisCombat`, `ThisGame`), a kind (`Any`, `Combat`, `Noncombat`,
`Excess`, `ExcessNoncombat`) and a measure (`Occurrences`, `TotalAmount`,
`DistinctSources`). "This way" reads back from the damage instruction through
`ObjectFilter::DamagedBy`, `ObjectFilter::DealtExcessBy`, `PlayerSet::DamagedBy`
and `Expr::ExcessDamage`.

**Yield so far.** Batches gave 286, 216, 166, 131, 84 and 235 complete cards from schema 46 to 50, about 30 forms each. The 235 came from walking a greedy set cover, so work from that chain, not from `blocker_records`: it counts a form's marginal cards after earlier picks. Prefer one arm over many rows: a variant shared between enums belongs in a sibling fallback, which removed 109 forms in one change.

**Review rules for primitives.** A primitive only stands in for a form with no reduction. It never overrides an invariant the reduced path rejected, and `rescue` in `lower.rs` enforces this on every family, after a row let a rule past the battlefield-scope check its reduced path applies. A test pinning the gap caught it. An Oracle hit rate is evidence, not approval. Accept only one rules-defined action, keyword or event that existing operations cannot express: `RevealHand` scores 100% and is still wrong, because `Reveal` exists. Trigger rows must not hide occurrence history or damage, whose semantics are structured; a test enforces this after a batch accepted `...ForTheFirstTimeEachTurn` on hit rate alone and an existing test caught it. A failing test that pins a gap is a finding, so read it before changing it. Audit disagreements so far were all loose rows, such as Map tokens exploring and "six-sided die", but each must be read, because one could be a corpus bug.

Rank work by `blocker_records` in the `ast check` report. It records the failure behind each named action and rule, past the first failure in a record. Do not rank by `named`, which includes children that only failed with their parent. Blockers still hide what lies inside a failed rule, so greedy figures remain upper bounds.

Hand-written lowerers are the exception from step 1 on. A form gets hand-written code only when a generated or registry path cannot express it, and the reason goes in this plan.

### Correctness has to scale with coverage

Coverage automation only moves wrong data faster. All of the card bugs in this round came from the source corpus, not from the lowerer, and each passed every existing gate.

| Check | Candidates | Confirmed templates | Yield |
|---|---:|---:|---:|
| Mining, tight thresholds | 256 | 26 | 10% |
| Mining, wide thresholds | ~300 | 8 | 3% |
| Mining, templates outside the first pass | 101 | 2 | 2% |
| Rule table | 24 | 9 | ~40% |
| One token per phrase occurrence | 81 | 64 | 79% |
| Render-back, read by a person | 277 cards | 33 | 40 cards, 14% |
| Render-back second pass, with named rows and lints | 469 cards | 109 | 159 cards, 34% |
| Render-back third pass, newly complete cards | 454 cards | 73 | 92 cards, 5% read directly |
| Unused captures in a template | 224 | 11 | 5% |

`--audit-literals` runs all of these as a Go test. Mining needs no hand-written knowledge, and it found bugs nobody wrote a rule for. Its limit is that it compares one template's English with that template's output. It cannot see an error shared by most templates for a phrase, or an error that only appears when templates compose. So the remaining steps are:

1. **Card-level differential: first pass done.** A statistical comparison of each ability with its Oracle line was too noisy to use: 11,511 findings, mostly IR structure, and lines do not align with abilities when modes or `Scoped` wrappers split them. Asking the narrower question worked: does a word from the card's Oracle text appear anywhere in that card's source record? That found 76 wrong cards, all in single templates (#26-#33), which the template audit had missed because presence-only rules pass a template with two clauses and one token. The working rules moved into `literalCountRules`, so they now gate every template. 30 further cards only changed spelling from `UntilEndOfNextTurn` to `UntilTheEndOfPlayersNextTurn`. Words with long exception lists (`up to`, `unless`, `another`, `double`) were not reviewed and remain open.
2. **Source-to-AST differential: done, as `ast value-audit`.** The lowerer is the one place a clause can vanish without any corpus check seeing it, so this compares each complete record's source with its AST. Integers and fieldless forms keep their spelling through reduction. A form most records keep but one record lacks was dropped on that path. Of 1,027 forms, three were flagged and all three were reviewed renames. Integers found one real drop, Dodecapod's two counters, which an ignored argument had lost, and two false positives that are now compared by magnitude. A form that is never kept was renamed, so the check says nothing about it. A grep of every lowering arm that discards a source field with `_` or `..` found 97, all read in a follow-on arm.
3. **Render-back: first pass done, as `ast render-back`.** It does not generate English. It mines word pairs between each complete card's Oracle text and the words of its AST identifiers, using a primitive's reviewed text, then lists the cards that break a pair holding across nearly every card. This needs no synonym table and sees what the template audit cannot, because it compares whole cards. Of 931 pairs with 6,409 card breaks, 277 cards were read: 40 were wrong, across 33 templates, and 4 more were doubtful and repaired. Reading the first rows, listing every capture a template drops, and sweeping every "another target" with no exclusion found 22 others. All 66 changed records are filed as #37-#42. The largest families were "your opponents control" encoded as yours, and lost "may" and "other". It is a report to read, not a gate: most pairs are habits of wording, so a zero count would mean nothing. `data/ast_reviewed_render.json` lists the cards accepted per pair, so a new card reopens that pair. After the repairs 917 pairs still break, and most of that report is unread. It still cannot see meaning: reading Boon Reflection, not any check, found that a replacement body must cancel the event it replaces. A second pass read 469 more cards and repaired 159 records (#43 to #51). Ranked rows alone confirmed about 14 cards, near 5%. Named-row and lint sweeps gave the rest, so the next pass starts from sweeps: isn't/aren't, doesn't/don't, or more/or greater, owner, only, and static "other".
4. **Keep filing upstream**, using the same short format.

Awesome Presence (#33) now pays per blocker through `PayManaForEach`.

The corpus bugs found so far are a lower bound. Do not read an empty literal audit as proof the corpus is right.

### Iteration speed

Full checks are cheap enough to run after every change. Measured on 33,529 records on a shared machine with load around 20 to 60:

| Check | Serial, unoptimized | Now |
|---|---:|---:|
| `ast check` | 3m21s | 5.3s |
| `ast pipeline-check` | 4m38s | 19s |
| `ast export-unified` | 1m22s | about 2s |
| AST test execution | 43s | 3.8s |
| Rebuild after an edit | 50s | 10s |

The largest costs were not in lowering: unbuffered artifact writes took 27s of `pipeline-check`, a serial fold took 26s, and one fixture test took 16s of the test run. Keep it this way:

- **Per-record work goes in the `map` closure of `corpus::map_cards`.** `visit` runs on one thread and only merges. Results arrive in line order, so reports do not depend on scheduling. `MTGISH_THREADS` overrides the worker count, which defaults to the core count capped at 32.
- **Measure before optimizing.** Time the phases first. Sampling was flat here, and phase timers found both main-thread costs immediately.
- **Prove a speedup changed nothing.** Compare reports against the previous run. Only `inputs` may differ, because it hashes the sources being edited.
- **Do not use `--release`, and do not raise `opt-level` on our own crates.** Optimizing `rust_syntax` did not finish in about 7 minutes. Setting `mtgish-ast` to `opt-level = 1` cut `ast check` to 3.6s but took rebuilds from 10s to about 3 minutes. Judge a build setting by the whole edit-and-check loop, not by run time alone. The dev profile optimizes dependencies and drops debug assertions from `mtgish-ast`.
- **Fixture sweeps share one parallel pass.** Look at any test over one second.

Changing a profile for dependencies costs one rebuild of about 6 minutes.

Known remaining cost: `ast check` still uses about 110s of CPU, mostly `serde_json::Value` churn from `inspect::value`, `named_forms` and `Inventory::form`, which re-serializes a subtree at every node. Wall time does not justify more work yet.

**Current execution scope: finish normalization through staged, generated rewrites before expanding Cantrip support.**

The compiler now separates structural consolidation, recipe expansion, reference binding, and final validation/export. Preserve the existing semantic IR and completed lowerers as the final target and migration bridge. Broaden the generated rewrite registry instead of continuing the direct, handwritten adapter loop. The full-tree stage inventory drives work even when a parent ability/layout cannot yet bind. Structural preservation and semantic completion are separate gates; unresolved intermediate data must never count as a final normalized card.

The default build and coverage check validate typed Rust lowering, reference and result invariants, serialization, and preservation of the existing corpus. They do not invoke the Cantrip generator. Existing backend sources remain behind the optional `cantrip` Cargo feature and explicit `check-cantrip` command. Compatibility with the evolving normalized schema is deferred to the backend milestone; a report records `backend_checked` so an unchecked backend cannot be mistaken for either supported or unsupported behavior. New normalized forms do not require matching engine adapters or gameplay scenarios before they can land.

**Separate operations from the structure around them.**

The normalized AST should contain typed representations for abilities, announcement choices, structured instructions, operations, queries, expressions, events, and durations. Rust enums and named payload structs should express these contracts directly. Use separate entity types and validated references to reject invalid combinations.

| Existing specialization | Normalized concept |
| --- | --- |
| `DrawACard`, `DrawNumberCards`, player-wrapped drawing | `Draw` with explicit players and amount |
| Permanent, spell, sacrificed-card, and exiled-card damage | `DealDamage` with an explicit source reference, recipients, amount, and damage properties |
| Zone-specific return, exile, and put actions | `MoveObjects` with an object selection, destination, placement, and entry specification |
| Single and each permanent destruction | `Destroy` with an object collection and regeneration policy |
| Single and each counter placement | `PutCounters` with recipients, counter kind, and amount |
| Permanent and player effect creation | `CreateContinuousEffect` with affected subjects, changes, duration, and capture policy |
| Flashback and graveyard ability grants | Intrinsic casting permission, alternative cost, required resulting spell types, and a conditional stack-exit replacement; ordinary continuous ability grants |
| Optional actions and payments | Explicit decisions and payment results around ordinary operations |
| Numerous modal forms | Mode bounds, repeat policy, mode costs, target specifications, and bodies |
| `Reflexive_*` variants | An initiating operation and a separate reflexive ability tied to its result |
| Turn-scheduled `CreateFutureTrigger*` variants | One delayed-trigger operation with an existing event matcher, eligibility gate, optional expiration/intervening-if, and captured lexical program |
| Specialized numeric forms | Arithmetic, properties, query aggregation, event fields, and history expressions |

Keep distinct verbs where their meaning matters: drawing, discarding, milling, sacrificing, destroying, and ordinary movement remain distinguishable even if the backend ultimately moves cards between zones. Give keyword mechanics typed parameters and reusable definitions. Count their forms when reporting simplification; moving complexity into an uncounted enum is not a reduction.

Aim initially for roughly 50–80 ordinary operation kinds plus a small set of structural forms. Treat this as a design hypothesis to test against exhaustive mappings, not a quota that permits incorrect generalization. Prefer adding a parameter or composition rule when an existing operation already has the required semantics. Add a new form only when a concrete card requires a distinction the current model cannot express.

**Resolve references and preserve observations explicitly.**

Replace implicit contextual names such as `Ref_TargetPermanent` and `NumCardsDiscardedThisWay` with typed, scoped bindings. Distinguish the ability source, its controller, target slots, trigger participants, chosen values, and prior operation results. Nested programs must not overwrite a shared implicit “this way” context.

Operation results should expose the information subsequent instructions need: selections, actual affected objects, before and after identities, captured characteristics, actual amounts, payment completion, and associated events. Define when each expression is evaluated and whether it reads live characteristics or captured information.

Preserve these distinctions throughout lowering:

- Targets selected during announcement versus choices made during resolution; per-object predicates versus constraints on the whole selection.
- “If you do” continuations versus “when you do” reflexive triggered abilities with their own targets and stack entries.
- Ordered iteration versus a simultaneous operation over a collection, including choices collected before a batch is applied.
- An attempted operation versus what actually occurred after restrictions, prevention, or replacements.
- Objects before and after zone changes, including last-known information and links between abilities.
- Resolving effects that capture an affected set versus static effects that evaluate a live query.
- Trigger conditions, intervening conditions, frequency limits, event grouping, and controller-relative durations.
- Proposal transformations in replacement effects versus ordinary effects performed as part of the replacement.

Preserve semantic instruction boundaries. A sequence of instructions, several implementation calls belonging to one instruction, and a simultaneous event batch are separate concepts. The current `ActionList` does not encode all these distinctions, and some templates combine multiple sentences into one effect payload. Retain grammar provenance and add explicit boundaries where needed; the existing serialized AST cannot reliably reconstruct everything that was discarded. Punctuation alone is insufficient to infer instruction structure.

The rules review must distinguish ability boundaries, resolution instructions, and parts of a continuous effect. CR 113.2c uses paragraphs for abilities; CR 608.2c/e permits ordered instructions within clauses; CR 613.6 describes effects spanning layers. That last rule does not itself establish an atomic creation boundary. Neither sentence boundaries nor verb counts alone prove grouping. The earlier same-sentence pump/keyword assumption, including Subversive Acolyte's finer `gets`/`gains` split, remains unverified by a specific ruling. Its +1/+1 modifier is not a counter placement. Preserve this uncertainty before backend batching or boundary-driven optimization; syntax regressions do not prove rules correctness. The current official rules are [effective September 25, 2026](https://media.wizards.com/2026/downloads/MagicCompRules%2020260925.pdf).

Add the official [Firesong and Sunspeaker rulings](https://magic.wizards.com/en/news/feature/dominaria-release-notes) to semantic fixtures: one damage instruction over multiple recipients differs from two damage instructions, and explicit life gain differs from life gain caused by lifelink. These provide independently documented event-grouping evidence. No official ruling for the precise Subversive Acolyte/Engineered Plague/Endangered Armodon combination was found; keep that scenario identified as an inference requiring verification.

**Use Forge to guide abstraction and Cantrip to test executable meaning.**

[Forge's factory](../forge/forge-game/src/main/java/forge/game/ability/AbilityFactory.java) separates record kind, effect API, parameters, targets, and subabilities. Its [effect vocabulary](../forge/forge-game/src/main/java/forge/game/ability/ApiType.java) is a useful comparison for shared operation families. Express the corresponding contracts with typed Rust data.

Cantrip is the later backend target. Generate ordinary Rust card modules with static `CardDef` values and named callbacks. Its `Effect` signature is `fn(&mut dyn Game, &StackItem) -> Result<(), Suspend>`; generated code can use deterministic local variables and propagate suspension through `?`. Lower filters and conditions into named callbacks, and reuse `cantrip-mechanics` when the recipe matches. Keep function pointers, runtime IDs, scratch storage, and engine scheduling out of the portable AST.

| AST responsibility | Cantrip integration |
| --- | --- |
| Spell, activated, and mana abilities | `spell`, `ability`, `mana_ability`, and their metadata |
| Announcement targeting and modes | `TargetSpec`, selection constraints, modal definitions |
| Queries and past events | `Query`, characteristics, and event history |
| Choices and optional payments | Shared helpers or `Game` operations returning `Suspend` |
| Ordinary effects | Rules operations in `Game` and shared mechanics |
| Simultaneous effects | Dedicated batch APIs such as `damage_together`, `destroy_all`, and `sacrifice_each` |
| Triggers and reflexive abilities | Event matchers, triggered definitions, and `reflexive_trigger` |
| Continuous and replacement effects | Layer callbacks, durations, proposal transformations, and follow-up callbacks |

Cantrip's boundaries have separate purposes. `end_sentence` checks pending state-trigger conditions after changes with no event; `one_instruction` identifies calls belonging to the same instruction; `settle_once` defers related settling, such as conditional duration expiration during a control exchange. They do not grant priority or generally run state-based actions between instructions. Generate the appropriate API from semantic grouping, using Cantrip's own batch operations for simultaneous events.

Track Cantrip capability separately from AST coverage. A supported AST operation may need a backend adapter or an engine capability that does not yet exist. Such a gap must produce a precise diagnostic, not a claim that the AST cannot represent the card or that the card is executable. Follow Cantrip's repository instructions when making changes there.
